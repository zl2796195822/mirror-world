## 1. 核心未决架构问题 (Open Architecture Questions)

### Q1: Checkpoint 存储应当采用“全量快照”还是“分层增量快照”？

- **背景**: 外部研究（AI Town）的经验表明，全量加载与全量快照在实体规模扩大后会瞬间遭遇性能悬崖。
- **权衡**:
  - _方案 A (全量快照)_: 结构极其简单，Replay 还原只需一次反序列化即可就绪；但在 1,000 居民时，单个快照体积可能达到数兆字节，频繁存盘引发 I/O 尖峰。
  - _方案 B (增量快照 / Delta)_: 仅记录自上一 Checkpoint 以来变更的实体；存储极其节省，但重放还原依赖多层合并，容错复杂度上升。
- **后续行动**: 在执行 M2-T05 时起草《ADR: Checkpoint 存储格式与快照周期选型》，建议首版采用每 N 步一次全量轻量快照，不提早引入过度设计的增量树。

### Q2: 动作执行结果 (ActionResult) 的物理归属设计

- **背景**: 当前已实现 `action_requests` 记录入参，但未记录出参；客户端重复发送同一 `idempotencyKey` 时无法直接获得上次执行生成的实体状态或事件序号。
- **权衡**:
  - _方案 A (直接扩充 `action_requests` 列)_: 增加 `committed_seq: bigint` 与 `result: jsonb`。简单直接，单表完成幂等与结果查询。
  - _方案 B (独立 `action_results` 表)_: 将请求意图与事实结果彻底拆分为两张物理表。解耦彻底，但增加单次写入的 Join/Insert 开销。
- **后续行动**: 建议在 M3 开启前，采用方案 A（单表扩充）以保持极高的单事务吞吐。

---

### Q3: 级联事件 (Event Cascade) 的事务边界划定

- **背景**: 未来业务必然涉及“动作引发事件 A，事件 A 的发生依据系统规则必然引发事件 B”（例如：轮班结束 -> 触发发薪）。
- **权衡**:
  - _方案 A (单事务原子全量追加)_: 在同一次 PostgreSQL 事务中，顺序计算所有衍生规则，连续分配 `seq, seq+1, seq+2` 并一次性提交。
    - _优点_: 强一致，绝不出现“下了班却没发薪”的中间半死状态。
    - _缺点_: 事务耗时增加，行锁持有时间拉长。
  - _方案 B (Saga / 异步事件总线解耦)_: 提交事件 A 后释放锁，通过消息队列在后续独立事务中处理事件 B。
    - _优点_: 单次事务极快。
    - _缺点_: 需要处理最终一致性、补偿机制与事件间隙时的状态漂移。
- **后续行动**: 核心物理与直接因果坚持方案 A；松散社会通知与宏观统计走方案 B。

---

### Q4: 多实例部署下的世界主循环独占租约 (World Lease)

- **背景**: 镜界 API 采用 Fastify 多实例部署，未来不能让多个后台进程同时推进同一个世界的时钟与心跳。
- **权衡**:
  - 依赖 Redis 的 Redlock / 分布式租约，还是利用 PostgreSQL 的 `SELECT ... FOR UPDATE SKIP LOCKED` 任务表？
- **后续行动**: 严格遵循《不可破坏边界：Redis 只能做 cache/lease/queue》。可使用 Redis 建立带 TTL 的 World Lock 租约，一旦持锁实例下线，其他节点在租约过期后接管。
