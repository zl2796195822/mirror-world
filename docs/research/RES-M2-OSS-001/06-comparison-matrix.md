# 06 - 30 维度全景技术对照矩阵 (Comparison Matrix)

本表严格依据实际源码分析编制，系统对照**镜界 (Mirror World)**、**AI Town**、**Concordia** 与 **OpenClaw World** 在 30 个关键架构维度的实现差异，并给出面向镜界的工程建议。

| #   | 评估维度 (Capability)       | 镜界 (Mirror World M2)                                         | AI Town (a16z-infra)                                                     | Concordia (Google DeepMind)                           | OpenClaw World (ChenKuanSun / Two-Weeks)                     | 镜界工程建议与决策 (Recommendation)                                             |
| --- | --------------------------- | -------------------------------------------------------------- | ------------------------------------------------------------------------ | ----------------------------------------------------- | ------------------------------------------------------------ | ------------------------------------------------------------------------------- |
| 1   | **World Authority**         | **PostgreSQL + World Kernel** 唯一写入口                       | **Convex 数据库 + 单线程 Engine** 独占所有游戏表                         | **Game Master (基于 LLM 的提示词中介)**               | **Node.js 进程内存状态 (WorldState)**                        | **KEEP**: 坚持 PostgreSQL 作为唯一权威事实源，拒绝内存主权与 LLM 主权。         |
| 2   | **Input Model**             | 强类型 **ActionRequest** 结构体 + JSON Payload                 | 数据库 **`inputs` 表**，带自增 `number` 和时间戳                         | 实体调用 `act()` 产出自然语言文本提议                 | 内存队列 **`pending` 数组**，通过 WebSocket 接收             | **KEEP**: 外部请求以数据形式存在；后续需补齐从队列/API 到 Kernel 的接入层。     |
| 3   | **Action / Command Model**  | **`@mirror/contracts` Zod 严格契约**，拒绝未知字段             | 显式 `inputs.ts` 对象与参数校验器 (Convex v)                             | `ActionSpec` 描述行动提示词、输出格式与选项           | 联合类型 `WorldMessage` (Position/Action/Chat/Join)          | **KEEP**: 保持严格 Zod 4.5.4 校验，禁止宽松未知字段进入内核。                   |
| 4   | **Validation**              | **Kernel Validator 纯函数**，严格分步校验权限/版本/资源        | `handleInput` 方法内业务前置条件检查                                     | 由 Game Master 通过 LLM 思维链裁决动作合理性          | Ingress 时执行基础边界包围盒与障碍物距离初筛                 | **KEEP**: 校验必须是确定性逻辑，坚决抵制由 LLM 承担前置条件验证。               |
| 5   | **Commit**                  | **PostgreSQL Transaction** 行级锁与原子提交                    | **Step 结束期** 一次性提交状态 Diff 并更新代数                           | LLM 产出 `event_statement` 并直接打入全局记忆         | 每一 Tick 内同步直接修改内存 Map 对象                        | **KEEP**: 状态变更与事件账本必须在同一个 PG 事务内提交。                        |
| 6   | **State Mutation**          | 显式 State Patch 与 SQL Update 结合，触发器拦截                | 内存中直接修改 JS 对象，Step 结束全量比对 Diff                           | 修改实体内部的 `Component` 状态字符串                 | 直接修改内存 Map (`positions.set()`)                         | **KEEP**: 生产代码严禁无审计痕迹的直接内存原地修改。                            |
| 7   | **Event Model**             | **Append-only `world_events`** 表，注册强类型与 Schema 版本    | **无全局 Event Ledger**；消息与状态 Diff 独立维护                        | 字符串打标 `[event]`，无结构化 Payload                | 200 条有限长度的内存环形历史缓冲区 `eventBuf`                | **KEEP**: 坚守可追溯追加写 Event Ledger，禁止采用有限环形缓冲。                 |
| 8   | **Ordering**                | **World-local 单调严格连续递增**                               | 按服务器接收时间戳 `received: Date.now()` 排序                           | 由 `Sequential` / `Simultaneous` 调度循环定义回合顺序 | 按内存数组入队 FIFO 顺序在单 Tick 内消费                     | **KEEP**: 序号不仅要递增，且必须在数据库中强制无间隙递增 (+1)。                 |
| 9   | **Sequence**                | `worlds.world_seq` 与 `world_events.seq` 一致性触发器强校验    | 递增的 `processedInputNumber` 与 `generationNumber`                      | 仅靠 Python 列表的隐式索引与遍历顺序                  | 仅有 `GameLoop.tickCount`，命令自身无 Seq                    | **KEEP**: 数据库级强校验序列连续性是防止绕过内核乱序写入的终极底线。            |
| 10  | **World Clock**             | **独立 World Clock 状态机**，支持锚点、倍率与冻结              | 双层时钟：60Hz Tick 与 1Hz Step，基于现实时间推移                        | `GenerativeClock` (由 LLM 推断) 或 `FixedIncrement`   | 固定 20Hz Node.js `setInterval` 定时器 (每 50ms)             | **KEEP**: 时钟必须作为一级物理概念入库并由显式函数驱动。                        |
| 11  | **Wall Clock Dependency**   | **逻辑解耦**：显式注入 Wall Clock，不可倒退，暂停时世界静止    | **强耦合**：Step 步进与输入收集直接依赖 `Date.now()`                     | **弱依赖**：主要依赖步数与 LLM 文本推断               | **强依赖**：Tick 调度与限流滑动窗口依赖 `Date.now()`         | **KEEP**: 保证 World Time 推进完全受控，不可被物理机漂移破坏。                  |
| 12  | **Randomness**              | 规格要求 **固定可注入 Seed** (PRNG)                            | 散落的非受控原生 `Math.random()`                                         | 依赖 LLM Temperature 采样与非确定性推理               | 初始坐标等逻辑直接调用 `Math.random()`                       | **KEEP**: 模拟内核代码严禁调用原生 `Math.random()`，必须统一 Seed 注入。        |
| 13  | **Determinism**             | **追求绝对确定性** (Replay-ready 架构)                         | **非确定性** (受网络时延、原生随机与 LLM 影响)                           | **完全非确定性** (由概率模型驱动叙事分支)             | **非确定性** (受网络包到达时序与内存时钟影响)                | **KEEP**: 核心世界事实演变必须支持重放还原。                                    |
| 14  | **Idempotency**             | **持久幂等**：`(world_id, idempotency_key)` 唯一约束与指纹对比 | 仅对 Input 赋予自增 ID，无 Payload 级去重和幂等保障                      | 无幂等机制 (依赖回合单次提议)                         | 仅 Two-Weeks 实现内存级 600s TTL 缓存，重启即失效            | **KEEP**: 维持 PG 事务内持久幂等，但须增强“重复请求能取回旧执行结果”。          |
| 15  | **Concurrent Actions**      | 并发请求通过数据库唯一行约束与行锁排队仲裁                     | 集中到单线程 Step 内顺序消费；但外层有 OCC 冲突风险                      | 串行引擎天然无并发；并行引擎交由 LLM 统一消解         | 网络并发接收，在单线程 Tick 内顺序排干处理                   | **KEEP**: 维持数据库行锁与快照隔离，避免外部并发破坏内核一致性。                |
| 16  | **Transaction Semantics**   | **PostgreSQL ACID 事务**，支持严格回滚与一致性检查             | **Convex 事务** (单 Step 内所有 Mutation 原子的)                         | 无数据库事务保障 (纯进程内存变量修改)                 | 无事务机制 (单步发生异常仅打印 console.error)                | **KEEP**: 必须保持世界状态 Patch 与事件在同一次 SQL 事务中提交。                |
| 17  | **World Isolation**         | **多世界天然隔离**：所有表与索引带 `world_id`                  | 多世界支持通过 `worldId` 隔离，但引擎按世界单例运行                      | 一个环境进程往往只跑一个虚拟社群场景                  | 单房间单 World 模式，跨世界需启动不同 Room                   | **KEEP**: 严格保留 `world_id` 复合主键与分区隔离能力。                          |
| 18  | **Actor Isolation**         | Actor 具有版本号 (`expectedActorVersion`) 与身份绑定           | Player 具有 ID，但数据混合在世界快照中由引擎加载                         | 实体为 Python 类实例，组件化挂载感知与执行            | Agent 作为 WebSocket 客户端或 Nostr 密钥对隔离               | **KEEP**: 推进基于 Actor 版本的乐观锁，防范过期意图并发修改。                   |
| 19  | **Persistence**             | **PostgreSQL 16 durable truth**                                | Convex Document Database 托管持久化                                      | 仅支持将整个 Python 环境状态 Dump 为 JSON 快照文件    | **纯内存运行**；重启后数据完全丢失 (仅依靠外挂中继)          | **KEEP**: 坚守关系型数据库持久底座，坚决不采用纯内存或非标准私有云库。          |
| 20  | **Snapshot / Checkpoint**   | 规划中 (M2-T05 任务，含 world/resident/item 等快照)            | 仅有当前活跃全量状态存储与 `HistoricalObject` 坐标缓冲                   | 支持环境全局 Dump/Load Checkpoint 回调                | 仅有 200 条有限历史缓冲区与定时 5 秒发送的完整状态广播       | **ADJUST BEFORE M2 GATE**: 必须尽快规范 Checkpoint 结构，避免全量快照膨胀。     |
| 21  | **Replay**                  | 规划中 (基于固定 Seed、有序事件账本与状态验证)                 | **不支持** (无事件源，无法回放历史)                                      | **不支持** (LLM 无法稳定复现推理)                     | 仅 Two-Weeks 提供最小 `InputRecorder` 文本记录器             | **KEEP**: 坚持 Event-Sourcing 重放路线，不降级为无重放玩具系统。                |
| 22  | **Projection / Read Model** | 规划中 (CQRS 架构：内核写事实，Projection 推向 3D/Web)         | Convex 响应式订阅 (`useQuery`) 直接将表状态推向前端                      | 直接通过 `make_observation` 生成局部文本观察          | 服务端定期广播全量 Snapshot 或 AOI 过滤的 Tick 切片          | **ADJUST LATER**: M7 采用 Colyseus 或轻量 WebSocket Projection 分离事实与渲染。 |
| 23  | **Async Agent Operations**  | 规划中 (M3/M5：Intent Queue + Worker Pool + Fencing Token)     | **核心亮点**：`startOperation` 挂起标记 + 异步 Action + `sendInput` 闭环 | Agent 在回合轮询时同步阻塞调用 LLM 接口               | 外部 Agent 异步请求，服务端非阻塞排队                        | **PORT PATTERN**: 深度采纳 AI Town 的异步操作状态机与完成闭环机制。             |
| 24  | **Scale Model**             | MVP 30 人；未来规划分级 LOD、空间分片与离线推演                | 仅支持数十人规模 (< 100)；全量反序列化导致无法上千                       | 仅支持 5~20 人小规模学术实验；Token 与时延成本极高    | 支持 50~100 个轻量 Agent 实时并发移动                        | **KEEP**: 坚决抵制把每个居民作为独立重型进程运行，规划三层 LOD。                |
| 25  | **Spatial Partitioning**    | 规划中 (地点 Location 图结构 + M7 3D 网格)                     | 无空间分区，全图实体遍历                                                 | 无空间分区，依靠文本描述地点归属                      | **核心亮点**：10×10 `SpatialGrid` 网格划分与半径 AOI 查询    | **PORT PATTERN**: M7 实时表现层直接借鉴 OpenClaw World 的 Grid 算法。           |
| 26  | **AI / LLM Dependency**     | **解耦隔离**：Kernel 零 LLM 依赖；LLM 仅产出候选意图           | **解耦隔离**：引擎与物理零 LLM；仅 Agent 交互层使用                      | **极高强耦合**：环境物理、裁决、时钟深度依赖 LLM      | **完全无耦合**：实时世界内核为纯规则与数学空间               | **KEEP**: 核心世界运转、时钟与经济系统坚决不绑定任何大模型。                    |
| 27  | **Failure Recovery**        | PG WAL 崩溃恢复 + 事务回滚保证不产生脏数据                     | 依赖 Convex 分布式日志与未消费 Input 重启处理                            | 无崩溃自愈，进程死掉需从头运行或手工载入 Checkpoint   | 服务崩溃所有状态丢失，完全无持久化容灾                       | **KEEP**: 依赖标准数据库容灾能力，不发明脆弱的私有容灾。                        |
| 28  | **Testability**             | **极高**：纯函数 Validator、内存快照注入、PG 集成测试          | 较高：Convex 内部支持模拟环境单测                                        | 较低：重度依赖 Mock LLM 输出，脆弱且难以回归          | 极高：纯 TypeScript 数学与数组测试，轻量敏捷                 | **KEEP**: 维持纯函数领域校验器与确定性测试套件。                                |

| 30  | **镜界复用方式**            | **ORIGINAL CORE (自研世界内核)**                               | **REFERENCE ONLY** (借 Agent 异步隔离与 Step/Tick 思想)                  | **REFERENCE ONLY** (借中介裁决模式；严禁借 LLM 权威)  | **PORT / REFERENCE** (借 Spatial Grid 与 AOI；借 Lanes 思想) | **KEEP**: 严格遵守复用分级，不将外部整体架构强塞进主仓。                        |
