# 09 - 仿真驱动机制研究：Tick 与 Event 的权责边界 (Tick-Event Model)

在构建“持续运行的数字社会”时，核心架构难题之一是如何驱动世界的演变：

- 是像传统游戏引擎那样，每秒对全图所有实体做固定频率的 **Tick（循环轮询）**？
- 还是像现代分布式事务系统那样，完全由 **Event（事件触发）** 驱动？
- 亦或是采用分层分级的 **Hybrid（混合模型）**？

严禁简单粗暴地得出“所有居民每秒 Tick 一次”的幼稚结论。在 30 居民阶段，每秒循环尚且轻快；但在 1,000 甚至 10,000 居民规模下，全量全频轮询将造成数以万计的无意义空转，导致数据库和 CPU 瞬间瘫痪。

---

## 1. 四种驱动范式技术比对矩阵

| 对照维度                 | 范式 1: 纯固定 Tick (Fixed Tick)<br>_(如 20Hz / 60Hz 游戏循环)_    | 范式 2: 可变步长 Tick (Variable Tick)<br>_(依据 Wall-clock 补差)_ | 范式 3: 纯事件驱动 (Event-Driven)<br>_(无心跳，仅靠行为触发)_ | 范式 4: 分层混合驱动 (Hybrid Tick + Event)<br>_(镜界推荐架构)_ |
| ------------------------ | ------------------------------------------------------------------ | ----------------------------------------------------------------- | ------------------------------------------------------------- | -------------------------------------------------------------- |
| **确定性 (Determinism)** | **极高**（固定 $\Delta t$，数学递推完全可复现）                    | **极低**（浮点数步长受机器负载波动影响，易发散）                  | **极高**（状态仅随因果事件跃迁，无时钟累计误差）              | **极高**（连续物理走本地/低频定步长，长期状态走事件懒计算）    |
| **计算性能与空转开销**   | **差**（无论实体是否静止，每个 Tick 都全量计算；开销 $O(N)$ 极高） | **中**（负载高时合并步数，但依旧全量遍历）                        | **极佳**（无行为即零计算开销，CPU 占用与活动量正比）          | **优**（低频心跳粗粒度调度，活跃实体精细步进，闲置实体零开销） |
| **重放复杂度 (Replay)**  | 较简单（保存输入流与初始 Seed 即可同步推演）                       | 极其困难（必须记录每个帧的微小时间差）                            | **极优**（顺序回放事件账本即得到最终状态）                    | **极优**（以事件账本为主轴，定点快照配合局部重放）             |
| **30 居民场景 (MVP)**    | 运行完美，CPU 消耗通常 < 5%，动效极其平滑                          | 运行良好，偶有掉帧追赶卡顿                                        | 动效难以连续平滑呈现，需客户端额外推演                        | **运行完美，工程实现极其干净**                                 |
| **1,000 居民场景**       | **严重瓶颈**：每秒 20,000~60,000 次实体更新，DB I/O 崩溃           | 步长剧烈拉长，模拟出现瞬移穿模                                    | 运行极其轻快，但缺乏自然的生理周期推进                        | **性能平稳，只对视口内或关键实体高频更新**                     |
| **10,000 居民场景**      | **彻底瘫痪**：服务器 CPU 与总线完全被空循环占满                    | **彻底瘫痪**：级联超时与重试风暴                                  | 扩展性极强，适合宏观统计与社会规则演进                        | **唯一可行路线**：结合空间 LOD 与事件驱动的懒求值模型          |

## 2. 镜界关键领域能力的驱动归属划分（核心结论）

不能把所有属性一概而论。镜界未来涉及的生理衰减、移动、工作、睡眠、经济，应当严格遵循**“连续空间与高频交互走 Tick，离散事实与长期因果走 Event”**的黄金法则：

### A. 哪些能力必须由 Event 驱动？（禁止用高频 Tick 轮询）

1. **经济交易与账户结算 (Economy & Payments)**：
   - 房租扣除、薪资发放、购物消费、税收。
   - **机制**：完全由计划事件（Scheduled Event / Job）或交互动作（ActionRequest）触发。严禁每秒轮询所有居民的钱包！
2. **睡眠与工时结算 (Sleep & Work Shift Summary)**：
   - **机制**：当居民进入睡眠时，产生 `RESIDENT_SLEPT` 事件，并在任务队列（BullMQ）中注册一个 `WAKE_UP_ALARM` 定时事件；起床时直接计算总睡眠时长并结算体力恢复，而不是在 8 小时内每秒 Tick 一次加体力。
3. **关系跃迁与重大记忆生成 (Relationships & Memories)**：
   - **机制**：仅在对话结束（`CONVERSATION_COMPLETED`）或重大事件发生时触发一次性评估与账本追加。

### B. 哪些能力适合由 Tick 驱动？

1. **连续空间移动插值与防穿模 (Movement & Path Following)**：
   - **机制**：客户端 60Hz 表现层插值，服务端空间服务器以 10Hz~20Hz 节奏处理在线居民的移动步进。
2. **局部碰撞与 AOI 视野更新 (Spatial Grid Rebuild)**：
   - **机制**：仅在有实体发生位移的区域，按固定低频（如 5Hz~10Hz）局部刷新网格。

### C. 最关键的设计：生理需求衰减的“懒求值（Lazy Decay via Event）”

- **传统错误做法**：每秒 Tick 10,000 次，给每个居民扣减 0.0001 的饥饿值（造成天量数据库 Update 和脏行）。
- **推荐正确做法（事件时钟懒计算模式）**：
  - 数据库中仅保存实体的 `needs_anchor_time` 与衰减速率参数 `decay_rate`。
  - **在任何事件发生前（如居民被查询、准备吃东西、准备工作）进行实时函数求值**：
    $$ ext{currentHunger} = ext{lastHunger} - ext{decayRate} imes ( ext{currentWorldTime} - ext{anchorTime})$$
  - 仅在居民真正发生行为并产生 Event 提交事务时，顺便更新最新的快照值与时间锚点。
  - **收益**：10,000 个在睡觉或离线的居民，在 8 小时内产生 **0 次** 数据库写入与 **0 次** CPU Tick 占用！

## 3. 镜界分级智能（Intelligence & Simulation LOD）规划建议

为保证未来从 30 人平滑过渡到 1,000+ 与 10,000+，建议确立三级模拟精度：

```text
[LOD 0 - 玩家视口内 / 活跃交互中] (30~100 人)
  - 驱动模型: 20Hz 服务端空间 Tick + 实时 WebSocket 增量广播 + 高频状态机。
  - 适用场景: 第一条街、正在与玩家对话或互动的 Resident。

[LOD 1 - 城市背景居民 / 正常作息中] (100~1,000 人)
  - 驱动模型: 低频粗粒度调度 (0.1Hz ~ 0.01Hz / 每 10秒~1分钟心跳一次)。
  - 适用场景: 在室内工作、走在远处的 NPC；仅维护宏观航点，不计算精细碰撞。

[LOD 2 - 离线 / 休眠 / 边缘区域] (1,000~10,000+ 人)
  - 驱动模型: 纯事件驱动 + 懒计算 (Zero Tick)。
  - 适用场景: 在家睡觉、闭店、宏观市民；仅依靠 Scheduled Event 触发下一日程，状态仅在唤醒时用闭式公式按需结算。
```
