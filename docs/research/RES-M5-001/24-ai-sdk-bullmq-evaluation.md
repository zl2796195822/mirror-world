# 24 - AI SDK 与 BullMQ 选型评估 (AI SDK & BullMQ Evaluation)

## 1. 评估背景与边界防线

在构建 M5 Agent Runtime 时，面临两大核心基础设施选型：

1. **模型调用与结构化提取层**：如何跨厂商统一调度 OpenAI、Anthropic、DeepSeek 与本地模型，并提取严格的 Zod Schema 意图？
2. **异步认知操作队列层**：如何实现多车道优先级、并发控制、任务超时重试与背压削峰？

在此必须重申**镜界绝对不可破坏的架构红线**：

> **Redis 永远只能作为缓存（Cache）、租约（Lease）与瞬态调度队列（Queue）！**
> **Redis 绝对不是持久世界事实（Durable World Truth）！**
> **无论队列技术选用为何，它仅承担“运行时认知编排（Runtime Orchestration）”；物理世界的唯一真理始终、且只能由 PostgreSQL 与 World Kernel 裁决承载！**

---

## 2. 候选一：Vercel AI SDK 深度评估

- **项目标识**: `ai` (Vercel AI SDK Core)
- **开源许可证**: **Apache-2.0** (完全合规，允许商业化与分发)
- **核心能力**:
  - 极度轻量且统一的 Provider 规范（`@ai-sdk/openai`, `@ai-sdk/anthropic`, `@ai-sdk/deepseek` 等）；
  - `generateObject` / `streamObject`：原生深度绑定 Zod Schema，强制模型通过 Tool/JSON Mode 输出强类型结构体；
  - 统一的 `TokenUsage`、`finishReason`、内置重试与 `AbortSignal` 支持；
  - 与特定 Web 框架完全解耦，支持在纯 Node.js / TypeScript 核心包中独立运行。

### 2.1 优劣势全面剖析

| 评估维度       | 表现评价 | 深度技术考据与分析                                                                     |
| :------------- | :------- | :------------------------------------------------------------------------------------- |
| **契约匹配度** | **极高** | 其 `generateObject({ schema: ActionIntentSchema })` 与镜界结构化意图契约天衣无缝匹配。 |
| **厂商解耦度** | **极高** | 业务代码仅面向 `CoreMessage` 与 Zod Schema，切换模型仅需改变配置，零业务代码污染。     |
| **依赖纯净度** | **优秀** | 核心包 `ai` 零重型系统依赖，无全局副作用。                                             |
| **许可证合规** | **PASS** | Apache-2.0 协议，商业友好，无感染风险。                                                |
| **潜在风险点** | **中等** | 版本迭代较快（从 v3 跃迁至 v4），需严格锁定次版本号，防止 upstream breaking changes。  |

### 2.2 裁决结论：`RECOMMEND (强烈推荐引入)`

> **裁决**：作为 M5 基础设施层实现 `ProviderPort` 的首选官方标准依赖。在后续开发中锁定版本并登记入 `THIRD_PARTY_REGISTER.md`。

## 3. 候选二：BullMQ (基于 Redis 的分布式队列) 深度评估

- **项目标识**: `bullmq` (Taskforce.sh)
- **开源许可证**: **MIT** (完全合规，商业友好)
- **核心能力**:
  - 基于 Redis Streams / Sets 的工业级高性能作业队列；
  - 原生支持 **多车道优先级 (Priority)**、**延迟作业 (Delayed Jobs)** 与 **并发上限 (Concurrency Cap)**；
  - 原生支持基于 Redis Key 的单居民防重排他锁与限流令牌桶（Rate Limiting）；
  - 具备完善的 Worker 心跳看门狗，宿主机崩溃时自动由其他节点认领僵尸任务。

### 2.1 优劣势与红线边界审查

| 评估维度           | 表现评价     | 深度技术考据与分析                                                                                              |
| :----------------- | :----------- | :-------------------------------------------------------------------------------------------------------------- |
| **车道与调度**     | **极佳**     | 完美落地 `LANE_FOREGROUND` 到 `LANE_MAINTENANCE` 的五级优先级与并发配额隔离。                                   |
| **削峰填谷力**     | **极强**     | 面对数百居民并发事件风暴时，能平滑排队并执行背压丢弃，有效保护云端 API 与后端内核。                             |
| **容灾与恢复**     | **优秀**     | Worker 崩溃时任务自动重试，状态可视化监控体系成熟。                                                             |
| **内存依赖度**     | **中等**     | 需维护独立 Redis 实例，但镜界基础设施架构已包含 Redis 用于缓存与租约。                                          |
| **与内核事实关系** | **必须警戒** | **严禁把 BullMQ 当做事件账本！**队列中的 Job 只是瞬态认知任务，丢弃任务仅代表居民本次不思考，绝不影响世界事实。 |

### 2.2 裁决结论：`CONDITIONAL RECOMMEND (有条件推荐引入)`

> **准入条件**：
>
> 1. **仅限运行时编排**：BullMQ 只能用于调度 `AgentOperation`，绝对不能用于持久化 `world_events` 或作为 ActionRequest 的唯一持久队列；
> 2. **无状态设计**：任务 Payload 只能保存 ID 指针与元数据，禁止在 Job 中保存大段游戏事实数据；
> 3. **从容降级**：当 Redis 发生不可用或清空时，系统必须能平滑退回“内存直通”或“Life Engine 纯确定性模式”，绝不能导致世界内核停摆。
