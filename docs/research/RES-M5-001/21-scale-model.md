# 21 - 梯次规模扩展模型 (Scale Model Architecture: 30 / 100 / 1,000 / 10,000)

## 1. 规模演进的系统分层哲学

一个优秀的系统架构，应当在初期保持极致简单（YAGNI 原则），同时在核心接口与实体契约上保留清晰的无锁无常驻设计，使得系统能够在不需要推倒重写核心的前提下，优雅跨越三个数量级的规模跃迁。

镜界为 **30 $\to$ 100 $\to$ 1,000 $\to$ 10,000** 居民制定阶梯式的运行时支撑方案：

```text
┌────────────────────────────────────────────────────────────────────────┐
│ 30 居民 (小镇微观社会): 单进程内存队列, 允许高频高保真剧情交互           │
├────────────────────────────────────────────────────────────────────────┤
│ 100 居民 (街区中观社会): 引入 BullMQ 优先级车道, 实施基础 LOD 调度      │
├────────────────────────────────────────────────────────────────────────┤
│ 1,000 居民 (城镇宏观社会): 纯事件驱动 + 严格 Token 配额 + 空间 AOI 裁切 │
├────────────────────────────────────────────────────────────────────────┤
│ 10,000 居民 (都市数字社会): 90% 处于休眠/确定性基线, 聚焦局部微观观察区 │
└────────────────────────────────────────────────────────────────────────┘
```

## 3. 详细阶段演进实施策略

### 3.1 阶段一：30 居民（精益启动，拒绝过度工程）

- **架构特征**：
  - 不需要配置复杂的分布式 Redis 队列集群，在 Node.js 进程内使用轻量级内存队列即可；
  - 允许 30 名居民以较高频率（人均每日 30 次）唤醒高阶大模型，用于生成极具戏剧冲突与个性化的日记、对话和邻里关系；
  - 核心工作聚焦于打通 `ObservationSnapshot`、`ActionIntent` 与 `KernelActionOutcome` 的闭环。

### 3.2 阶段二：100 居民（车道划分与 LOD 确立）

- **架构特征**：
  - 正式引入 BullMQ，落实 `LANE_FOREGROUND`、`LANE_CRITICAL` 等 5 个车道；
  - 启用 Intelligence LOD 评估器，将远距离背景居民压降到 `LOD-I1` 规则层；
  - 引入本地端侧轻量小模型（如 8B SLM）消化 60% 的日常对话，成本得到有效遏制。

### 3.3 阶段三：1,000 居民（纯事件驱动与空间 AOI 裁切）

- **架构特征**：
  - 废除任何形式的周期性全员轮询；只有当居民感知半径（AOI 半径 20 米）内发生强冲击事件时才触发唤醒；
  - 观察快照装配严格限制 Top-K 记忆与 Top-5 附近实体，防止数据库读取慢查询；
  - 设立小时级 Token 预算熔断器，单世界每小时上限受控。

### 3.4 阶段四：10,000 居民（宏观静息态与量子化激活）

- **架构特征**：
  - **量子化观察（Quantum Perception）**：远离人类玩家的所有居民处于宏观统计态（LOD-I0 休眠），由 Life Engine 每分钟粗粒度推演一次位置和生理状态；
  - 只有当人类玩家靠近某个街区时，该街区的居民才被“观察坍缩”激活为微观拟真态；
  - 绝不需要为了 10,000 居民在现阶段部署复杂的微服务中台，核心架构依靠纯函数与无状态设计即可自然向上扩展。
