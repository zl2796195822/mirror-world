# 22 - 认知会话策略架构对比与裁决 (Agent Session Strategy)

## 1. 核心问题：居民是否需要持久长连接聊天会话？

在传统基于大模型的聊天机器人架构中，开发者通常为每个用户维护一个长期的 `ChatSession`，每次用户说话时，把历史消息数组（`messages = [...history, newMessage]`）直接追加并持续发送。

若将该设计照搬至持久数字社会中的虚拟居民：

> 设想林默生活了 30 天，发生了 500 次对话与决策。如果维持一个“永久 Chat Session”，其对话历史将长达数十万 Token。每次思考都需要发送巨大的历史上下文，或者依赖云端提供商私有的 Assistant Thread 存储。

本节系统对比四种候选会话架构，为镜界 M5 做出最终技术路线裁决。

---

## 2. 四种会话架构方案深度对比

- **方案 A：永久会话模型 (Permanent Chat Session / Stateful Thread)**：每个居民在云端（如 OpenAI Assistants API）绑定一个长期的 Thread，所有历史决策持续追加。
- **方案 B：无状态操作 + 记忆检索注入模型 (Stateless Operation + Memory Retrieval) —— 推荐核心基石**：每次唤醒均为纯无状态 HTTP 请求，通过 M4 记忆引擎检索 Top-K 记忆片段拼装上下文，用后即焚。
- **方案 C：短命局部会话窗口模型 (Short-lived Session Window)**：仅在特定多轮事件（如持续对话）发生时创建临时 Session，空闲 60 秒后自动销毁归档。
- **方案 D：混合分层会话模型 (Hybrid: Stateless Default + Ephemeral Micro-Session) —— 最终推荐落地模式**。

### 2.1 全维度技术评估对比矩阵

| 评估维度               | 方案 A (永久会话)           | 方案 B (无状态+记忆检索)      | 方案 C (短命局部窗口)   | 方案 D (推荐混合模式)         |
| :--------------------- | :-------------------------- | :---------------------------- | :---------------------- | :---------------------------- |
| **Token 成本与增长**   | 灾难级 (二次方无限膨胀)     | **极低且恒定 (严格受限)**     | 良好 (仅对话期增长)     | **极低且恒定 (兼顾两者)**     |
| **上下文膨胀风险**     | 必然爆 Context Window       | **零风险 (固定分箱预算)**     | 极小 (窗口到期即清空)   | **零风险 (双重守卫)**         |
| **崩溃自愈与容灾**     | 极差 (依赖远端外部状态)     | **完美 (任意节点崩溃无损)**   | 良好 (丢失少量临时对白) | **极优 (主状态完全持久化)**   |
| **确定性与可重放**     | 彻底破坏 Replay 根基        | **极高 (输入严格受控可复现)** | 中等                    | **极优 (事件流完整驱动)**     |
| **厂商可移植性**       | 极差 (强绑定特定厂商Thread) | **极佳 (通用纯文本请求)**     | 极佳                    | **极佳 (支持任意云/本地端)**  |
| **长期心智真实度**     | 伪长记忆 (靠长文本堆砌)     | **真长期心智 (M4认知架构)**   | 缺乏跨会话长期沉淀      | **最佳 (短期生动, 长期沉淀)** |
| **多轮对话自然流畅度** | 极高 (原生保留上下文)       | 稍弱 (需依赖短反馈注入)       | 高 (会话内连贯)         | **极高 (对话期使用微窗口)**   |

## 3. 为什么坚决否决方案 A（永久会话）？

1. **厂商绑架（Vendor Lock-in）**：OpenAI 的 Assistants API 或 Anthropic 的会话机制属于厂商私有闭源协议。一旦厂商宕机、调价或下线该接口，整个镜界的“居民灵魂”将无法迁移至 DeepSeek 或开源本地模型。
2. **记忆不可修正与污染扩散**：若大模型在第 3 天产生了一次精神错乱或幻觉，该错误文本将永久保存在 Session Thread 中，在随后的 27 天内持续诱导模型发疯，系统无法像数据库一样精准修正某条特定历史。
3. **成本黑洞**：在长会话下，即使只回复一句“你好”，也要为前面累积的 50,000 Token 支付 Prefill 费用。

---

## 4. 推荐路线：方案 D 混合会话架构裁决

镜界正式确立**方案 D：以无状态决策为核心基石，辅以短暂多轮微会话（Stateless Core with Ephemeral Micro-Sessions）**：

```text
       ┌────────────────────────────────────────────────────────┐
       │                   日常状态 (95% 场景)                   │
       │  - 居民独立做日常决策、走动、购物、打工               │
       │  - 采用 [方案 B]: 纯无状态请求 (Stateless Operation)  │
       │  - 观察切片 + M4 Top-3 记忆检索 ──► 一次性推理 ──► 销毁│
       └────────────────────────────────────────────────────────┘
                                   │
                (触发与人类玩家或特定居民的持续多轮深度对话)
                                   ▼
       ┌────────────────────────────────────────────────────────┐
       │                 深度对话态 (5% 关键场景)                │
       │  - 激活 [方案 C]: 瞬态微会话 (Ephemeral Micro-Session) │
       │  - 在 Redis 暂存最多 5 轮对话气泡 (TTL = 120 秒)       │
       │  - 保障面对面交流的因果承接与上下文代词自然理解        │
       └────────────────────────────────────────────────────────┘
                                   │
                       (对话结束 或 超时 120 秒静默)
                                   ▼
       ┌────────────────────────────────────────────────────────┐
       │                     归档与终结闭环                     │
       │  - 销毁 Redis 中的瞬态微会话                           │
       │  - 生成世界事件: CONVERSATION_COMPLETED                │
       │  - 异步投递给 M4 提炼 1 条核心记忆摘要存入持久库       │
       │  - 居民回归 [方案 B] 纯无状态运行态                    │
       └────────────────────────────────────────────────────────┘
```

### 4.1 本裁决的终极价值：

- **既拥有无状态的高并发、低成本、高弹性和多厂商移植性**；
- **又兼顾了与人类玩家交流时多轮互动的自然流畅度**；
- **彻底将瞬态会话生命周期与持久记忆生命周期物理剥离**。
