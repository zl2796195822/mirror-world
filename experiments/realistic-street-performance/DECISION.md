# EXP-3D-002 技术决策与 M7 架构结论 (Decision Document)

---

## 1. 核心架构问题回答

### 1. R3F 路线是否仍推荐？
**推荐 (RECOMMENDED)**。
React 19 + `@react-three/fiber@9.7.0` 在写实街区、动态天气光照与多角色调度中表现出极佳的组件解耦能力。渲染循环与 React 状态隔离清晰，未出现内存泄漏或调度阻塞。作为镜界 Web 3D 渲染表现层完全成立。

### 2. Rapier 是否仍推荐？
**推荐 (RECOMMENDED)**。
`@react-three/rapier@2.2.0` 作为物理引擎，在 300m 街区的地面、台阶、15°斜坡、狭窄小巷与建筑碰撞体上均表现优异。
**关键边界条件**：必须将地面及主要承重碰撞体设置为厚度充足的地下实体（建议 $\ge 5$ 米），严禁使用 $0.1\sim 0.2$ 米的薄板碰撞体，以防止大帧耗时抖动下的物理穿透（Tunneling）。

### 3. Ecctrl 是否仍条件推荐？
**条件推荐 (CONDITIONALLY RECOMMENDED)**。
Ecctrl 2.0.2 的 `shapeCast` 模式在台阶拾级与斜坡行走上稳定可用。
**限制条件**：
1. 正式产品必须将其输入层与移动端虚拟摇杆、手柄以及自定义交互层全面解耦；
2. 狭窄转角与室内场景需自研摄像机防穿墙（Camera Occlusion Clipping）模块，避免默认弹簧臂在低矮天花板或窄巷内突变抖动。

### 4. 真实资产后的核心瓶颈是什么？
**核心瓶颈在于：未合批 VRM 人物的 Draw Calls 爆炸与骨骼蒙皮计算开销。**
单个未经优化的 VRM 带来 280+ 次 Draw Calls 与 70 万面片；静态建筑物即便增加 PBR 贴图，在合理视锥剔除与 Instancing 下开销可控，而动态骨骼角色是绝对的性能杀手。

### 5. 30 个 VRM 是否可行？
- **原始全量 VRM：绝对不可行 (INVIABLE)**。30 个原始模型同屏将产生 >1000 次 Draw Calls 与 >340 万面，低端设备与手机必崩溃；
- **Visual LOD + Lazy Loading 下：可行 (VIABLE)**。通过将远景角色转换为无骨骼的极简代理，近景仅保留 3~5 个高质量模型，帧率可稳定在 **70 FPS**。

### 6. 推荐的 LOD 模型是什么？
**三级 Visual LOD + 距离感应就近升降级**：
- **LOD 0 (< 20m)**：近景全量模型（面数控制在 $\le 18,000$ 面，Draw Calls 合并在 $2\sim 3$ 次内），60 FPS 逐帧骨骼更新，允许动态阴影；
- **LOD 1 (20m ~ 45m)**：中景减模模型（$3,000 \sim 5,000$ 面），骨骼计算跳帧降频至 15~20 FPS，关闭动态阴影；
- **LOD 2 (> 45m)**：远景极简代理（低模/法线广告牌，$< 500$ 面），0 骨骼蒙皮，基础着色。

### 7. 推荐的 Scene Chunking（场景分块）方案？
推荐采用 **glTF 资产切片 + 空间九宫格调度 (3×3 Grid Spatial Chunking)**。
首屏仅下载并激活出生区及邻近 Zone，其余区域通过后台 Web Worker 异步 fetch 与 parse。设置 20 米空间滞后区（Hysteresis），避免边界频繁挂载抖动。

### 8. KTX2 是否采用？
**必须采用 (STRONGLY ADOPT)**。
实测 KTX2 UASTC 相对 PNG 节省 **99% 的网络传输体积**，并且进入显卡显存后保持压缩态（节省 75%~87% VRAM）。对于移动端防止 WebGL 上下文因超显存崩溃是绝对必需项。

### 9. Draco 与 Meshopt 推荐哪一个？
**强烈推荐 Meshopt，不推荐 Draco**。
- Draco 虽然压缩比略高，但其解码器庞大（~1 MB），且 CPU 解码耗时较高，在流式加载时易引起主线程卡顿；
- Meshopt 解码器极小（仅 29 KB），依托 SIMD WASM 解码速度高出一个数量级（约 1 GB/s），是 Web3D 实时流加载的最优解。

### 10. Desktop 初版性能预算 (Desktop Budget)

| 指标 | 初版预算上限 | 实测对照 |
|---|---|---|
| **初始 JS 产物体积 (Gzip)** | $\le 1.5\text{ MB}$ | 1.23 MB |
| **初始场景资源 (Scene MB)** | $\le 8.0\text{ MB}$ | 1.05 MB (纹理) |
| **近景高质量 VRM 配额** | $\le 5\text{ 人}$ | 3~5 人 |
| **同屏总 Draw Calls** | $\le 400\text{ 次}$ | 310 次 (5人) / 986 次 (30人LOD) |
| **同屏最大可见面数** | $\le 1,200,000\text{ 面}$ | 719,180 面 (5人) |
| **显存占用 (Texture VRAM)** | $\le 150\text{ MB}$ | 83.8 MB ~ 120.3 MB |
| **目标帧率** | $\ge 60\text{ FPS}$ | 63 ~ 74 FPS |

### 11. Mobile 端的核心风险是什么？
1. **高 Retina DPR 像素填充率**：移动端若直接以 DPR 3.0 绘制，像素计算量激增；必须强制钳制为 `dpr <= 1.5`；
2. **WebKit Jetsam 内存强制熔断**：移动端内存上限严苛，近景 VRM 配额必须收紧至 $\le 3$ 人；
3. **长时间运行发热降频**：需动态根据电池/发热状态降低远景更新率。

### 12. M7 的最大技术阻碍 (Blocker) 是什么？
**虚拟居民美术资产的减面与合批自动化工业流水线**。
如果美术提交的 VRM 依然是单人 70 万面、数十个材质球的原始模型，客户端无论如何优化架构都无法支撑数字社会的群体表现。必须在资产管线中强制执行 Bake Atlas 合批与多级网格减面。

### 13. 是否需要 EXP-3D-003？
**需要 (RECOMMENDED)**。
在进入 M7 正式业务开发前，建议执行 `EXP-3D-003` 专项攻坚：
- 重点验证「自动化轻量化 Avatar 资产规范（合批/减面）」；
- 接入「Meshopt 压缩模型流式解压」；
- 真实手机局域网多设备物理验证（闭环 `PHYSICAL MOBILE DEVICE = UNVERIFIED` 状态）。

---

## 2. 最终实验结论

$$\mathbf{PASS\_WITH\_BOUNDARY}$$

实验证明：镜界所规划的写实青禾街区在 Web 端具备成立的技术可行性，但必须受限于 Visual LOD 约束、KTX2 显存压缩以及 Avatar 材质合批规范。
本实验在此结论下正式闭环，不进入正式 M7。
